### ✅ BGE rerank 抗超时与可观测加固（f29f129）

**背景**：生产 chunk 平均 ~300 字 × N 条让 bge-reranker-v2-m3（cross-encoder，attention O(n²)）推理 30s+，命中 5s timeout 静默降级。curl 用短文测试（25字/条）亚秒级回，无法复现生产负载。

**加固**：
- `RerankService` 响应处理器修 `consume + toString` 二次读取 bug
- `rag.rerank.timeout-ms` 5s → **30s**，connect 单独配 3s
- `rag.rerank.candidate-cap=4` + `max-chars-per-doc=500` 控制推理量（6+×500字 已逼近 30s，砍到 4 留余量；max 匹配存储上限，零内容损失）
- `RAGService` 状态加权排序后按 `candidate-cap` 截一刀
- `BGE_RERANK_PREP` 日志暴露 `avgRaw/maxRaw/truncated` 等真实 chunk 长度
- SLF4J `{0.3f}` 占位符不识别，改 `String.format`（`AnswerCredibilityService` 同源修复）
- `application.yml` 清理孤儿 `cache.type` 字段（spring 不认 `cache.type`，只认 `spring.cache.type`）

**效果**：BGE rerank 超时降级走 fallback 的概率显著下降，日志字段可解释调参。

### ✅ PaddleOcrExtractor 修响应处理器同源 bug（cfb05dd）

**背景**：`RerankService` 排查 BGE 超时时发现的同源 bug：`HttpClientResponseHandler` 里先 `EntityUtils.consume` 把响应体读完丢弃，再 `toString` 再读一次，实体流已被关闭，`toString` 拿到空串。

**症状**：`PaddleOcrExtractor` 的 `timeout-ms=10000` 暂时没爆只是症状没显现，响应体被悄悄丢弃后会判 `text` 为空、走空串兜底路径。

**改造**：简化为单行 lambda，由 HttpClient 在退出时负责 `consume`。

## 今日小问题

1. **BGE rerank 仍是性能瓶颈**：30s timeout 是"够用"而不是"快"，cross-encoder attention O(n²) 决定长文档场景下 rerank 永远重。需要观察 `BGE_RERANK_PREP` 日志里 avgRaw 分布，决定是否进一步压 cap。
2. **JSONB → TEXT 迁移要写一次性脚本**：QA 历史表已有数据，`references_info` 字段类型变更需要 PG migration 用 `USING references_info::text` 兜底，ALWAYS check 老数据没坏。
3. **Milvus 2.5.6 BM25 Function 在 standalone 模式 OK，distributed 模式需要先建 sparse index**：本地 standalone 测试没问题，正式环境如果是 distributed 部署要先确认 sparse index 创建顺序。
4. **PaddleOcrExtractor 同源 bug 在生产可能已经静默跑了很久**：日志里检查一下历史 `text=""` 兜底的出现频率，估算 OCR 实际识别成功率。
