# 2026-08-28 开发日志

## 今日目标
提升 RAG 检索精度和系统健壮性：多文件批量上传、3 层重排流水线、HTTP 超时可控、chat 异常精细分类。

## 完成情况

### ✅ 多文件批量上传（DocumentController）

**改动**：`POST /api/documents/upload` 接收 `MultipartFile[] files`，循环处理每个文件，返回 `ApiResponse<List<JobAck>>`。
- 单个文件失败不影响其他文件（per-file try-catch，失败标记 `REJECTED`）
- Spring multipart 上限从默认 1MB / 10MB 提到 `100MB / 500MB`（覆盖扫描件大 PDF + 批量）
- 共享元数据（title/documentNumber/status/effectiveDate）一次性提交，循环内只换文件

**前后对比**：
- 之前：每次只能传 1 个，前端要循环 N 次，N 次 HTTP 握手 + N 次鉴权
- 现在：1 次请求搞定整批，单个失败明确告知是哪个文件

### ✅ 3 层重排流水线（RAG / Milvus / Rerank）

**背景**：之前 Milvus 召回 top-20 后只按现行/已废止加权 → top-5。两个问题：
1. SemanticChunker 滑窗切分导致 top-5 里同 docId 占 3-4 条，挤掉其他文档相关片段
2. 缺少语义精排，向量距离未必反映真实相关性

**改造**：在 Milvus 召回之后、喂 LLM 之前插入 3 层渐进式重排：

| 层 | 内容 | 失败降级 |
|---|---|---|
| 1a | 相似度阈值过滤（默认 `0.32`） | — |
| 1b | 同 docId 去重（per-doc 配额 `2`） | — |
| 1c | 状态加权排序（现行 × 2.0 / 废止 × 0.3） | 这是降级路径 |
| 3 | MiniMax rerank API 语义精排 | 退回到层 1c |

**Milvus 服务端 status 过滤**：`searchVectors(vec, topK, expr)` 新增 expr 重载，粗召回阶段直接 `status == "现行"`，网络和内存减半。

### ⚠️ MiniMax rerank 端点 404，临时关闭

**调查**：`POST https://api.minimax.chat/v1/rerank` 返回 404 HTML 页面（不是 JSON 业务错误）。
**实测所有候选路径**：
- `/v1/rerank`、`/v1/text/rerank`、`/v1/rankings`、`/v1/rank`、`/v1/reranker` 全部 404
- 国际站 `api.minimaxi.com` 同样情况
- 仅 `/v1/text/chatcompletion_v2` 和 `/v1/embeddings` 是真正的 API 端点

**结论**：MiniMax 公开 API 没有 rerank 端点（营销页 `/rerank` 跳转到官网产品介绍）。
**决策**：`rag.rerank.enabled=false`，降级到层 1c（status 加权 + 去重 + 阈值）。代码保留，未来切到 Cohere / Jina / BGE 自部署时只需改 base-url。

### ✅ HTTP 客户端超时控制（MiniMaxConfig + MiniMaxService）

**改动**：
- 新增 `minimaxHttpClient` Bean：共享连接池，connect=3s / response=5s（默认）
- chat 调用方覆盖：response=30s（LLM 生成 token 慢）
- 切换到 httpclient5 API：`Timeout.ofMilliseconds()`、`response.getCode()`、`EntityUtils.toString(entity, StandardCharsets.UTF_8)`

**价值**：避免 MiniMax 长时间无响应时拖死整个请求线程。

### ✅ MiniMaxException 异常层级

新建 `MiniMaxException` 抽象基类，4 个子类区分语义：

| 类型 | 触发场景 | RAGService 处理 |
|---|---|---|
| `Timeout` | socket / connect timeout | （保留为 String 返回，HTTP 200） |
| `Business` | HTTP 4xx（鉴权/参数/配额） | 抛 → RAGService 返回业务文案 |
| `ServerError` | HTTP 5xx | 抛 → 同上 |
| `Network` | DNS / 连接被拒 / 解析失败 | 抛 → 同上 |

**价值**：调用方按类型决定日志埋点和降级策略，监控和告警能精准区分。

### ✅ 空候选短路（RAGService.ask()）

dedup 后 `items.isEmpty()` 直接返回 `"未检索到相关政策资料..."`，跳过 rerank / context 构建 / LLM 调用，避免空上下文浪费 token 拉低质量。

### ✅ 降级日志统一标记 `[FALLBACK] key=value`

所有降级路径统一前缀，便于运维 grep / 监控：

| 日志 | 触发场景 | 级别 |
|---|---|---|
| `[FALLBACK] embed_fallback=true reason=...` | MiniMax embed 失败，用 hash 向量 | warn |
| `[FALLBACK] rerank_fallback=true reason=...` | MiniMax rerank 失败 / 返回 null | warn（异常时 error） |
| `[FALLBACK] chat_timeout=true reason=socket_timeout` | chat 读取超时 | warn |
| `[FALLBACK] chat_error=true reason=business\|server_error\|network` | chat 业务/服务端/网络异常 | **error** |
| `[FALLBACK] short_circuit=true reason=no_candidates_after_filter` | 空候选短路 | info |

**分级原则**：实际异常（HTTP 4xx/5xx、网络层）走 error 级别触发告警；降级路径（fallback 到旧逻辑）走 warn。

### 🐛 SLF4J 格式占位符修复

**问题**：日志输出 `similarity: {:.4f}` 字面量，没被格式化。
**原因**：项目用 SLF4J 1.x，不支持 `{:format}` 语法。
**修复**：`((Number) r.get("similarity")).floatValue()` + `String.format("%.4f", sim)`。同时 `top{}` 改为 `top#{}` 避免相邻 placeholder 误判。

## 已知小问题

1. **MiniMax 无公开 rerank 端点**：当前禁用，等官方开放或切换厂商
2. **dedup 后只剩 10 条**：20 条召回里同 docId 占比较多（top-20 是基于 `topK * 2`，可考虑加 `topK * 3` 缓冲）
3. **chat 业务异常时 references 仍计入引用计数**：失败响应也触发了 doc.setReferenceCount()，需在 catch 后判断 answer 是否为业务文案决定是否跳过
4. **rerank 当前总是降级**：实际生产等同于关闭 rerank，监控里看不到任何 rerank 调用成功记录
