### ✅ #3 references_info JSONB→TEXT 迁移脚本

**背景**：昨天 commit `3e2e089` 把 `qa_history.references_info` 从 JSONB 改为 TEXT，schema.sql / QaHistory.java 已对齐新类型，但 **存量数据库** 列还是 JSONB，Hibernate `ddl-auto:update` 不会主动 ALTER 跨类型列（特别是破坏性类型变更）。

**新增文件**：
- `src/main/resources/db/migration/V20260831__qa_history_references_info_jsonb_to_text.sql`
- `src/main/resources/db/migration/README.md`

**脚本要点**：
- 用 `DO $$ ... $$` 包一层 idempotent 检查，先查 `information_schema.columns` 确认当前类型是 JSONB
- 是 JSONB → `ALTER COLUMN ... TYPE TEXT USING references_info::text`（USING 子句对每行反序列化，零数据丢失）
- 不是 JSONB → NOOP + `RAISE NOTICE`，可重复执行不炸
- 脚本末尾附 3 条手动校验 SQL（类型确认 / 抽样 JSON 合法性 / 非空率），不直接执行

**README 要点**：
- 文件命名约定 `V<YYYYMMDD>__<scope>_<description>.sql`
- 适用场景：仅存量 DB（schema.sql 已对齐新类型，全新部署不需要）
- 运行方式：psql `--single-transaction` 干跑
- 新增脚本流程：注释背景 / 风险 / 锁表时长 / 校验 SQL / 在 README 登记

### ✅ 动态 candidate-cap（f29f129 之后的接力）

**背景**：昨天加固 rerank 抗超时（cap=4 / max-chars=500），但 `BGE_RERANK_PREP` 日志显示生产 chunk 平均 ~300 字，固定 cap=4 是"够用"而不是"最优"：
- 短文档（< 200字）→ cap=4 浪费，短推理很快，可多召回
- 长文档（> 400字）→ cap=4 已经接近 30s，应该再砍

**改造**：
- `application.yml` 新增 `rag.rerank.dynamic-cap` 配置段：
  ```yaml
  dynamic-cap:
    enabled: true
    short-threshold-chars: 200
    long-threshold-chars: 400
    short-cap: 6
    mid-cap: 4
    long-cap: 3
  ```
- `RAGService` 新增 `computeEffectiveCap(List<RagItem>)` 方法：
  - 计算 `avgRawChars`（候选 chunks 的 text 平均字符数）
  - 按阈值选档（short / mid / long）
  - 应用 `Math.min(tierCap, rerankCandidateCap)` clamp，防止异常配置导致 cap 爆炸
- 第 5b 步截断前调用，结果打印到 `[BGE_RERANK_CAP]` 日志

**档位语义**：
| avgRawChars | tier | cap（受 candidate-cap clamp） |
|---|---|---|
| < 200 | short | min(6, candidate-cap) |
| 200~400 | mid | min(4, candidate-cap) |
| > 400 | long | min(3, candidate-cap) |

**clamp 设计的取舍**：
- 想让 short 档 cap=6 真正生效 → 必须把 `candidate-cap` 提到 6+
- 当前 `candidate-cap=4` 是绝对上限 → 短档实际也只截到 4，short-cap 配置仅起"上限信号"作用
- 现状偏保守：动态档只决定"少召回"（long 档 cap=3）vs "中等召回"（mid 档 cap=4）
- 想更激进 → 提高 candidate-cap 到 6 或 8，再观察 BGE_RERANK 日志

### 参数调优（基于真实数据）

下午首版上线后跑了一条真实 query："我是9610模式的跨境电商，做退货需要满足什么条件？"

**观测到的实际情况**：
```
[BGE_RERANK_CAP] tier=mid avgRawChars=381 tierCap=4 configuredCap=4 effectiveCap=4 items=14
[BGE_RERANK_PREP] candidates=4 truncated=0 avgRawChars=401 maxRawChars=500 avgSentChars=401 totalRawChars=1605 totalSentChars=1605 cap=500
[BGE_RERANK] success candidates=4 returned=4 elapsedMs=24887 scoreRange=[-9.313, 5.092] avg=-3.383
```

**暴露两个问题**：

1. **mid 档 cap=4 仍接近超时**：`elapsedMs=24887` 距 30s 超时只剩 1.1s，CPU/GPU 抖动即 fallback
2. **全 items 平均系统性低估**：`computeEffectiveCap` 算的 avgRaw=381（全 14 条），但实际送 rerank 的 4 条 avgRaw=401（更长）。原因是排序靠分数，长 chunk 内容多匹配得分天然偏高 → 长 chunk 冒顶

**修复**：

| 改动 | 位置 | 改前 | 改后 |
|---|---|---|---|
| `long-threshold-chars` | application.yml | 400 | **300** |
| `mid-cap` | application.yml | 4 | **3** |
| `long-cap` | application.yml | 3 | **2** |
| top-K 估算 | RAGService.computeEffectiveCap | `items.stream()` | `items.stream().limit(refK)` where `refK = min(items.size(), rerankCandidateCap)` |
| 日志格式 | RAGService.computeEffectiveCap | `(tier, avgRaw, tierCap, configuredCap, effectiveCap, items)` | `(tier, avgRaw, refK/items, tierCap, effectiveCap)` |

**预期效果**（同一条 query）：
- refK = 4（top-configuredCap），avgRaw = 401（与 BGE_RERANK_PREP 实测一致）
- 401 > 300 → long 档 → cap=2
- 估算 rerank 时间：2 × ~500 字 ≈ 1000 字 ≈ **~12s**（vs 改前 24.9s）

**改后的日志输出预期**：
```
[BGE_RERANK_CAP] tier=long avgRawChars=401 (4/14 items) tierCap=2 effectiveCap=2
```

**top-K 选取 refK = configuredCap 而不是 top-10 的理由**：
- top-10 会包含"如果 cap=10 我们会多送的 6 条"，污染预测
- top-configuredCap 永远偏向保守（高估负载 → 选更激进 cap → 更安全）
- 当 cap=4（典型）：完全准确
- 当 cap=2（long 档）：top-4 多含 2 条长 chunk，轻微高估 → 仍然更安全
