## 问题1：嵌套条款切片不完整

### 业务痛点
当前正则 `(?<=\\n\\n)(?=第[一二三四五六七八九十百千0-9]+[条章节])` **只匹配 `第X条` 和 `第X章`**，无法识别嵌套结构如 `第一条第一项`、`第一条第二项`。

这导致：
- `第一条第一项`、`第一条第二项` 会被合并进同一 chunk
- 当条款内容超长时，可能把多个项截断到不同 chunk，检索时语义碎片化

### 怎么改造
扩展正则或引入多级锚点识别：
```java
// 当前：只识别一级条款
Pattern.compile("(?<=\\n\\n)(?=第[一二三四五六七八九十百千0-9]+[条章节])");

// 改进：识别多级条款结构（条/章/节/项）
Pattern.compile("(?<=\\n\\n)(?=第[一二三四五六七八九十百千0-9]+[条章节款项])");
```

或在 `TextNormalizer` 阶段注入额外锚点标记。

### 预期结果
- `第一条第一项`、`第一条第二项` 被识别为独立条款边界
- 每个嵌套条款独立成 chunk 或在超长时内部再滑动切分
- 检索结果能准确定位到具体条款项

## 问题2：条款引用文本被误切

### 业务痛点
政策文档中经常出现引用性文本，如：
- `将第三条修改为："..."`
- `根据第二条的规定，制定本细则`
- `删除第一条中的第二项`

这些文本**不是独立条款**，但当前切片逻辑没有区分"条款定义"和"条款引用"，导致：
- 引用文本被错误地作为独立 chunk
- 或混入相邻 chunk，造成语义混淆

### 怎么改造
在 `TextNormalizer` 阶段引入**条款引用检测**，区分：
1. **条款定义**：以 `第X条` 开头的新条款（保留锚点）
2. **条款引用**：文中出现的 `第X条` 但前面有 `将/根据/按照/修改/删除` 等关键词（降级处理）

可增加字段 `isClauseDefinition: boolean`，或在切片时过滤掉纯引用段。

### 预期结果
- 引用文本不作为独立条款入库
- 检索结果中条款定义与引用文本正确关联
- 避免"将第三条修改为..."这类文本单独成一个无意义的 chunk

## 问题3：Chunk 状态粒度为 Document 级别

### 业务痛点
当前 `status` 字段打在 `PolicyDocument` 级别：
```java
// PolicyDocument.java
private String status = "现行";  // 整篇文档一个状态

// IngestionService.java
meta.put("status", doc.getStatus());  // 每个 chunk 继承文档状态
```

如果一篇文档中**部分条款已废止、部分继续生效**（如"关税法修订版，保留第一章、废止第二章"），整篇文档会被标记为单一状态，导致：
- 已废止条款的 chunk 带着"现行"标签被检索出来
- 有效条款可能因文档状态被错误过滤

### 怎么改造
两种方案：

**方案A：Chunk 级状态字段**
```java
// DocumentChunk.java 增加
@Column(name = "chunk_status", length = 20)
private String chunkStatus;

// IngestionService.java 修改
meta.put("status", resolveChunkStatus(doc, chunk));  // 根据条款查表或规则判断
```

**方案B：条款-状态映射表**
```
clause_status_map:
  - document_id: 123
    clause_anchor: "第一章 第一条"
    status: "现行"
    - clause_anchor: "第一章 第二条"
    status: "废止"
```

切片时查询映射表填充每个 chunk 的状态。

### 预期结果
- 检索结果能区分哪些条款是现行、哪些已废止
- 用户可按状态过滤检索结果
- 支持同一文档内混合状态的场景

## 问题4：固定 chunkSize 破坏条款完整性

### 业务痛点
当前滑动窗口使用固定 `chunkSize=500`、`overlap=50`：
```java
for (int i = 0; i < trimmed.length(); i += step) {  // step = 500-50 = 450
    int end = Math.min(i + chunkSize, trimmed.length());
    String slice = trimmed.substring(i, end);  // 可能拦腰截断完整条款
}
```

问题：
- 一个完整的 `第二条`（假设600字符）可能被截断到两个 chunk
- 检索时只能召回半个条款，语义不完整
- 条款边界是语义硬边界，不应被固定窗口打断

### 怎么改造
**优先级策略：条款完整性 > chunk 大小阈值**

```java
// 1. 条款长度在容忍范围内（≤ chunkSize × 1.5），保持完整
if (trimmed.length() <= chunkSize * 1.5) {
    out.add(new Chunk(trimmed, anchor, idx++));
    continue;
}

// 2. 超长条款内部滑动切分，但继承同一 anchor
int step = chunkSize - overlap;
for (int i = 0; i < trimmed.length(); i += step) {
    int end = Math.min(i + chunkSize, trimmed.length());
    // 智能断点：往前找最近的句号/分号/逗号，避免截断句子
    end = findGoodBreakPoint(trimmed, i, end);
    String slice = trimmed.substring(i, end);
    out.add(new Chunk(slice, anchor, idx++));
}

// 3. 好断点查找逻辑
private int findGoodBreakPoint(String text, int start, int end) {
    // 在 [start, end] 范围内往前找最近的断点
    for (int i = end - 1; i >= start; i--) {
        char c = text.charAt(i);
        if (c == '。' || c == '；' || c == '！' || c == '？') {
            return i + 1;  // 断在句号后
        }
    }
    return end;  // 没找到就用原始断点
}
```

### 预期结果
- 短条款（≤750字符）保持完整，不被切分
- 超长条款内部滑动切分，但每个子 chunk 共享同一 anchor
- 检索结果能返回完整条款，而非被截断的碎片

## 问题5：文档编号评分二元化（0/1），无法识别引用正确但解读错误

### 业务痛点
```java
float citationScore = cited ? 1.0f : 0.0f;  // 只有0和1两个值
```
当前实现只要 LLM 在答案中提到了文档编号（如"海关总署公告2023年第10号"），citationScore 就得 1.0 分。

**问题场景：**
- LLM 引用了正确的文号，但**瞎编了具体条款内容**
- 例：检索到"海关总署公告2023年第10号第一条"，但 LLM 说"根据该公告第一条，企业需..."，而实际上该公告第一条根本没有这条规定
- 这种"引用正确但解读错误"的情况无法被当前评分体系捕捉
- 更严重的是：**LLM 可能编造完全不存在的文号**（如"海关总署公告2023年第999号"），软约束在大压力下会失效

### 怎么改造
**硬约束方案：文号真实性核验**

LLM 压力大时软约束（Prompt 指令）会失效，需要程序层面的硬校验：

```java
public CredibilityResult evaluate(float topSimilarity, List<QaResponse.Reference> references, String answer) {
    // 1. 从答案中提取引用的所有文号
    Set<String> citedDocNumbers = extractDocNumbers(answer);

    // 2. 去数据库核验文号真实性（硬约束）
    List<String> verifiedNumbers = documentRepository
        .findByDocumentNumberIn(citedDocNumbers)
        .stream()
        .map(PolicyDocument::getDocumentNumber)
        .collect(Collectors.toSet());

    // 3. 计算真实引用比例
    float citationScore = citedDocNumbers.isEmpty() ? 0.0f
        : (float) verifiedNumbers.size() / citedDocNumbers.size();

    // 4. 标记无法核实的文号
    List<String> invalidNumbers = citedDocNumbers.stream()
        .filter(n -> !verifiedNumbers.contains(n))
        .toList();

    if (!invalidNumbers.isEmpty()) {
        log.warn("[CREDIBILITY] unverified docNumbers: {} in answer: {}",
                invalidNumbers, answer.substring(0, Math.min(100, answer.length())));
    }

    // 5. 综合评分（文号真实性直接影响 citationScore）
    float score = topSimWeight * topSimilarity + citationWeight * citationScore;
    String level = ...;
    boolean hasUnverified = !invalidNumbers.isEmpty();

    return new CredibilityResult(score, level, verifiedNumbers.size() > 0, hasUnverified, invalidNumbers);
}
```

**免责声明追加场景：**
```java
case "UNVERIFIED_CITATION" ->
    "⚠️ 部分引用来源无法核实，答案仅供参考，请以原文为准。";
```

### 预期结果
- 文号不存在时直接剔除该引用，降低置信度
- 硬约束不依赖模型自觉，大压力下依然有效
- 用户看到"部分引用来源无法核实"，知道需要自行核实

## 问题6：只看 top1 相似度，不反映整体检索质量

### 业务痛点
```java
float score = topSimWeight * topSimilarity + citationWeight * citationScore;
// topSimilarity 只是 rerank 后第1名的分数
```

**问题场景：**
| 情况 | top1 | top2 | top3 | 当前评估 | 实际检索质量 |
|------|------|------|------|---------|------------|
| A | 0.92 | 0.15 | 0.12 | 高可信 | 不稳定，top1 可能过拟合 |
| B | 0.92 | 0.89 | 0.87 | 高可信 | 稳定，多条高度相关 |
| C | 0.55 | 0.52 | 0.48 | 中可信 | 整体偏低但均衡 |

三种情况 top1 相同，但**实际检索置信度差异巨大**。只看 top1 会漏掉"top1 偏高但其余极低"这种异常情况。

### 怎么改造
引入**相似度分布指标**：
```java
public CredibilityResult evaluate(float topSimilarity, List<QaResponse.Reference> references, String answer) {
    // 计算相似度统计量
    float[] similarities = references.stream()
        .mapToFloat(QaResponse.Reference::getScore)
        .toArray();

    // 方案A：引入方差/标准差
    float variance = calculateVariance(similarities);
    float stabilityScore = 1.0f - Math.min(variance * 10, 1.0f);  // 方差大则稳定性低

    // 方案B：引入 top1 - top2 gap
    float topGap = similarities.length >= 2 ? similarities[0] - similarities[1] : 0f;
    // gap 过大说明 top1 孤立，不稳定

    // 综合评分
    float score = topSimWeight * topSimilarity
                + stabilityWeight * stabilityScore
                + citationWeight * citationScore;
}
```

### 预期结果
- 能识别"top1 偏高但其余极低"的异常检索
- 评分更全面地反映整体检索质量
- 不稳定检索触发更谨慎的免责声明

## 问题7：三档免责声明不区分场景，无法指导用户正确行动

### 业务痛点
```java
case "medium" -> "基于检索到的政策资料，但相似度有限，仅供参考，不构成法律建议。";
case "low" -> "未检索到高度相关的政策资料，以上内容仅供参考...";
```
当前只有两个档位的免责声明，且不区分具体失败场景：

| 实际场景 | 当前提示 | 问题 |
|---------|---------|------|
| 检索到1条，低相似度 | "相似度有限" | 无法指导行动 |
| 检索到多条，互相冲突 | "相似度有限" | 用户不知道是冲突 |
| 检索为0，完全没匹配 | "未检索到..." | ✅ 相对合理 |
| 检索到多条但都偏低 | "相似度有限" | 与场景1重复 |

用户看到免责声明后**不知道该怎么做**——是换关键词？核实法条？还是联系专业人员？

### 怎么改造
**按失败场景定制免责声明：**

```java
public String disclaimer(String level, String scenario) {
    if (level.equals("high")) {
        return "";  // 高可信，无需提示
    }

    return switch (scenario) {
        case "NO_RESULT" ->
            "⚠️ 未检索到相关政策资料，建议尝试其他关键词，或联系海关专业人员确认。";
        case "LOW_SIMILARITY" ->
            "⚠️ 检索到相关资料但相似度有限，答案仅供参考，请核实相关法规原文。";
        case "CONFLICTING_RESULTS" ->
            "⚠️ 检索到多条相互矛盾的政策资料，建议查阅原文或咨询专业人员。";
        case "SINGLE_RESULT" ->
            "⚠️ 仅检索到一条相关资料，答案仅供参考，建议交叉验证。";
        default ->
            "⚠️ 检索置信度有限，答案仅供参考，不构成法律建议。";
    };
}
```

场景判断逻辑：
```java
public String detectScenario(List<QaResponse.Reference> references, float topSimilarity) {
    if (references == null || references.isEmpty()) {
        return "NO_RESULT";
    }
    if (references.size() == 1) {
        return topSimilarity < 0.6 ? "LOW_SIMILARITY" : "SINGLE_RESULT";
    }
    // 检查 top1 与 top2 是否冲突（相似度差值 < 0.1）
    float topGap = references.get(0).getScore() - references.get(1).getScore();
    if (topGap < 0.1) {
        return "CONFLICTING_RESULTS";
    }
    if (topSimilarity < 0.6) {
        return "LOW_SIMILARITY";
    }
    return "DEFAULT";
}
```

### 预期结果
- 用户看到免责声明能知道具体出了什么问题
- 每种场景给出明确的下一步行动指引
- 提升用户体验，减少无效重复提问

## 问题8：文档级提取策略（整篇PDFBox或整篇OCR），混合型PDF质量差

### 业务痛点
当前 `PdfExtractorFactory` 是**文档级**判断：

```java
// 当前：要么全走 PDFBox，要么全走 OCR
if (looksLikeScan(r)) {  // 整篇文档是否疑似扫描件
    ocr.extract(file);  // 整篇走 OCR
}
```

**问题场景：**
```
一本 PDF，前50页是原生文本，后5页是扫描件
  → 整篇走 OCR → 前50页识别质量下降（OCR 对原生文本不如 PDFBox）
  → 或者整篇走 PDFBox → 后5页内容丢失
```

一本政策文件可能混合多种页类型，当前策略会导致部分页面质量差。

### 怎么改造
**页面级检测 + 混合提取：**

```java
// 逐页判断，每页独立选择提取器
for (int i = 0; i < pages; i++) {
    String pageText = pdfBox.extractPage(i);
    if (looksLikeScanPage(pageText, i)) {  // 每页单独判断
        pageText = ocr.extractPage(i);  // 该页走 OCR
    }
    allText.append(pageText);
}

// 页面级扫描件判定逻辑
private boolean looksLikeScanPage(String pageText, int pageIdx) {
    // 该页字符数过少
    if (pageText.length() < 50) return true;
    // 该页文字都是图片渲染的（如表格转图片）
    if (containsImagePlaceholder(pageText)) return true;
    // 该页乱码率过高
    if (garbageRate(pageText) > 0.3) return true;
    return false;
}
```

### 预期结果
- 混合型 PDF 每一页都能用最佳方式提取
- 原生文本页保持高识别质量
- 扫描件页自动降级到 OCR

## 问题9：PDF后清洗缺失 + 表格结构丢失

### 业务痛点
当前 `TextNormalizer` 只有基本清洗，没有针对政策文档的后处理：

**缺失的清洗：**
- 页眉页脚、页码会被当正文切片 → 污染 chunk
- 重复水印噪声 → 干扰语义
- 表格结构丢失 → 变成一堆对齐文字

**表格丢失的后果：**
政策文档中表格是重要内容载体（如税率表、许可证条件表），变成线性文字后：
- 检索时只能返回一堆对齐的文字，无法还原表格语义
- 用户看到的是乱掉的表格，而不是 Markdown 表格

### 怎么改造
**PDF 后清洗流程：**
```java
// 后清洗流程
String cleaned = pdfCleaner.removeHeaderFooter(text);      // 去页眉页脚
cleaned = pdfCleaner.removeRepeatedWatermark(cleaned);    // 去重复水印
cleaned = pdfCleaner.normalizePageNumbers(cleaned);       // 去页码

// 表格检测 + 转换为 Markdown
List<TableBlock> tables = tableDetector.detect(cleaned);
for (TableBlock table : tables) {
    String mdTable = table.toMarkdown();  // 转为 markdown 格式
    cleaned = cleaned.replace(table.rawText, mdTable);
}

// 然后再切片
List<SemanticChunker.Chunk> chunks = new SemanticChunker().split(cleaned);
```

表格 Markdown 格式示例：
```
| 序号 | 商品名称 | 税率 |
|------|----------|------|
| 1    | 化妆品   | 50%  |
```

### 预期结果
- 页眉页脚页码被去除，不污染 chunk
- 表格保持 Markdown 结构，检索时能正确展示
- 水印噪声被过滤

## 问题10：批量上传缺少限流与队列积压告警

### 业务痛点
批量上传文件时，并发触发多个 `ingestionService.processAsync()`，没有：
- **限流**：所有请求同时打向 embedding 服务，可能被打爆
- **队列积压告警**：队列满了 HTTP 线程会兜底执行，但用户不知道
- **优雅拒绝**：队列满时应该返回明确提示，而不是让 HTTP 线程卡住

当前 `CallerRunsPolicy` 只是兜底策略，不是真正的限流。

### 怎么改造
- 引入令牌桶/漏桶限流（Guava RateLimiter 或自定义）
- 队列大小超过阈值（如 80%）时触发告警（可利用 Actuator metrics）
- 队列满时返回 503 + retry-after 头，而不是 CallerRunsPolicy 硬扛

### 预期结果
- embedding 服务不会被突发流量打爆
- 运维能提前知道队列积压
- 用户得到明确的"服务繁忙，请稍后重试"提示

## 问题11：任务状态无分层，中断残留无清理

### 业务痛点
**状态无分层：**
```java
// 当前只有一个 job 级别状态
DocumentIngestJob.Status: PENDING → RUNNING → SUCCESS / FAILED
lastError: "extraction empty"  // 只有异常消息，没有阶段分类
```
用户不知道是 PDF 提取失败、OCR 失败、向量化失败、还是 Milvus 入库失败。

**中断残留：**
用户批量上传时如果中途关闭浏览器：
- PolicyDocument + IngestJob 已创建
- 部分 Milvus 向量已入库（不完整的 chunk）
- 无清理机制，检索到脏数据

### 怎么改造
**状态分层：**
```java
// 引入分阶段状态
public enum Stage { PENDING, EXTRACTING, CHUNKING, EMBEDDING, INSERTING, SUCCESS, FAILED }
public enum FailureReason {
    FILE_CORRUPT,      // 文件损坏
    OCR_FAILED,        // OCR识别失败
    EXTRACTION_EMPTY,  // 提取为空
    EMBED_FAILED,      // 向量化失败
    MILVUS_FAILED      // Milvus入库失败
}
```
增加 `stage` 和 `failureReason` 字段，失败时分类写入。

**中断残留清理：**
- 增加 `cancelJob(jobId)` 接口，中断时调用
- 增加 TTL 机制：RUNNING 状态超过 30 分钟未更新则视为 abandoned，触发清理
- 或者在 `processAsync` 入口检测 `job.status` 是否仍为 RUNNING（防重复执行）

### 预期结果
- 用户能看到每个文档具体失败在哪个阶段、什么原因
- 中断上传不会留下残留向量
- 支持手动取消任务并清理

## 问题12：多轮对话超过3轮后全量送入Prompt，token浪费

### 业务痛点
当前 `buildHistoryContext` 只保留最近3轮，全量拼接送入 Prompt：

```java
Page<QaHistory> page = qaHistoryRepository
    .findBySessionIdOrderByCreatedAtDesc(sessionId, PageRequest.of(0, 3, ASC, "createdAt"));
// 对话超过3轮后，早期对话被丢弃
```

问题：
- 对话轮次多了之后 Prompt 越来越长，token 浪费
- 早期对话可能与当前问题相关，但被丢弃
- 没有语义压缩，相同主题的对话没有聚合

### 怎么改造
**滚动窗口 + 历史摘要：**

```java
// 对话历史超过 N 轮时，压缩早期对话
List<QaHistory> allHistory = qaHistoryRepository.findBySessionIdOrderByCreatedAtAsc(sessionId);

if (allHistory.size() > MAX_ROUNDS) {
    // 早期对话用 LLM 生成摘要
    String earlyHistory = concatenateEarlyRounds(allHistory);
    String summary = llm.summarize("请简要概括以下对话的主题和关键结论：\n" + earlyHistory);

    // 只保留摘要 + 最近3轮
    context = summary + "\n\n" + recent3Rounds;
} else {
    context = allHistory;
}
```

### 预期结果
- 对话超过上限后早期对话被压缩成摘要
- Prompt 长度可控，不会无限膨胀
- 关键信息不会因轮次增加而丢失

## 问题13：政策库变更后Cache不主动失效，返回过期答案

### 业务痛点
当前使用 `@Cacheable` 但无主动失效机制：

```java
@Cacheable(value = "qa", key = "#request.question + '|' + (#request.userConditions ?: '')")
public QaResponse ask(QaRequest request) {
```

问题：
```
政策文档 A 新增/废止 → Milvus 向量更新
  → 用户搜相关问题
  → 命中旧缓存 → 返回基于旧向量的答案 → 幻觉
```

### 怎么改造
**监听政策库变更事件，主动失效相关缓存：**

```java
@EventListener
public void onPolicyChanged(PolicyChangeEvent event) {
    // 按政策编号失效相关 cache key
    cacheManager.evict("qa", "政策编号:" + event.getDocNumber());
    cacheManager.evict("qa", "条款锚:" + event.getAnchor());
    // 或者失效所有（简单粗暴）
    cacheManager.clear("qa");
}
```

触发时机：
- 政策文档新增时
- 政策文档状态变更（现行→废止）时
- 政策文档删除时

### 预期结果
- 政策库变更后相关缓存立即失效
- 用户不会拿到基于过期向量的答案
- 数据一致性得到保障

## 问题14：OCR识别置信度无记录，低质页面无提示

### 业务痛点
当前 `usedOcr` 只有 true/false，没有置信度信息：

```java
// OcrExtractor 返回
return new ExtractionResult(text, pages, true, elapsedMs, name(), null);
// 缺少 confidence 字段
```

问题：
```
某页 OCR 识别置信度很低，内容可能有误
  → 用户检索到该 chunk → 不知道这段可能识别错误
  → 误以为政策原文就是这样 → 基于错误信息做决策
```

### 怎么改造
**记录 OCR 置信度元数据：**

```java
// OCR 识别时记录置信度
OcrResult result = ocr.recognize(image);
float confidence = result.confidence();

// 低于阈值时打标记
if (confidence < LOW_CONFIDENCE_THRESHOLD) {
    meta.put("ocr_low_confidence", "true");
    meta.put("ocr_confidence", String.valueOf(confidence));
}
```

**检索结果返回时检查：**
```java
// RAGService 构建答案时检查
if ("true".equals(chunk.get("ocr_low_confidence"))) {
    answer += "\n\n⚠️ 本段来自图片 OCR 识别，内容可能存在识别误差，请核实原文。";
}
```

### 预期结果
- OCR 置信度低的页面在检索结果中有明确提示
- 用户知道该段内容可能识别不准确，需要核实原文
- 避免基于错误识别信息做决策
